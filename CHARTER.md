# The Churchill Charter

This document defines the principles that guide Churchill: how it is built, how it grows, and how contributors should approach improving it.

Churchill is not just a collection of files and features. It is a system designed around openness, understanding, and intentional design. Every decision should make Churchill easier to use, easier to modify, and easier to contribute to.

## Core Principles

## Freedom

Churchill belongs to its users.

The system should remain open, editable, and transparent. Users should be able to understand their system, modify it, and make it their own without unnecessary restrictions.

## Accessibility

Powerful and beautiful software should not require years of experience to use.

Churchill should provide a welcoming experience for beginners while still respecting advanced users who want full control through the terminal.

## Transparency

A system should explain itself.

Files, folders, scripts, and decisions should be documented so contributors can understand not only what something does, but why it exists.

## Intentionality

Every feature should have a purpose.

Churchill should not add complexity for the sake of appearance, popularity, or technical achievement. Features, animations, and design choices should exist because they improve the experience.

## Humanity

Churchill is designed for people.

Performance, efficiency, and technical excellence matter, but they should serve the person using the system.

## Simplicity

Complexity is a cost.

If something can be made simpler without reducing capability, it should be.

## Longevity

Churchill should grow carefully.

New features should be designed with future contributors and users in mind.

A system should not only work today. It should remain understandable years later.

# Documentation Rules

## Every directory must explain itself.

Every major directory should contain a README explaining:

- Why it exists.
- What belongs there.
- Important files and components.
- How it connects to the rest of Churchill.

A contributor should never have to guess where something belongs.

## Every important file should explain itself.

Configuration files, scripts, and complex components should document their purpose and usage.

Comments should explain why something exists, not simply repeat what the code already shows.

## Every feature must justify itself.

Before adding a feature, contributors should be able to answer:

1. Why does this exist?
2. Why does it belong in Churchill?
3. Can another person understand and maintain it in the future?

If a feature adds more complexity than value, it should be reconsidered.

# Contribution Philosophy

Contributions are not only additions of code.

Improving documentation, fixing mistakes, simplifying systems, and improving accessibility are all valuable contributions.

Churchill should grow like a living system: carefully, openly, and with room for others to contribute.

Every contributor should leave Churchill easier to understand than when they found it.
